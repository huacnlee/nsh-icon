# Contributing Guide

Contributions are welcome. If you find a bug or have an idea, please open an issue or submit a pull request.

Please write clean code that follows the style and organization of the existing code, and make sure all checks pass.
Please submit **one PR that does one thing**: it is easier to review and faster to merge.

## Scope: what nsh-icon accepts

nsh-icon gives [NSH](https://github.com/longbridge/nsh) apps the icons of popular icon sets, drawn as vectors in the
text color, with only the icons an app uses in its binary and bundle. It follows how
[GPUI Kit's assets](https://github.com/longbridge/gpui-kit/tree/main/crates/assets) handle Lucide, and names icons as
[shadcn.io](https://www.shadcn.io/icons) and [Iconify](https://iconify.design) do.

Welcome, with no prior issue:

- **Bug fixes** in drawing, sizing, color or accessibility, in Rust or TSX, on any platform NSH supports.
- **Updating a set** to a newer upstream release (see "Updating a set").
- **Size and performance**: anything that keeps unused icons out of an app, or makes drawing cheaper.
- **Docs and the agent skill** (`skills/nsh-icon`), so apps and coding agents use icons rather than characters.

A new icon set, or new public API in `nsh-icon`, needs an issue first and a maintainer's agreement. A set is accepted
when:

- It is widely used, maintained, and drawn with `currentColor` (one color that follows the text).
- Its license allows redistributing its icons in a library (MIT, ISC, Apache-2.0 and the like). A set whose license
  restricts that, such as Remix Icon from 4.9, is pinned to its last release under a permissive license, or left out.
- It comes from its upstream release, pinned by version and SHA-256, not from a copy or a third-party repackaging.

The boundary with NSH:

- **Drawing belongs to NSH.** `nsh-icon` draws with NSH's `svg` element and image loader; it does not render SVG
  itself. A missing primitive (TSX has no `<Svg>`) goes upstream, following NSH's contributing guide.
- **Do not change NSH to fit this crate.** Solve it here first, with NSH's existing APIs.

## Layout

- `nsh-icon` (the repository's root): the `Icon` type, `icon()`, `labeled_icon()`, `icon_set!` and the TSX `<Icon>`
  (`src/tsx.rs`, the native module `nsh-icon`). It holds no icons.
- `sets/<set>/`: one crate and nshm per set, `nsh-icon-<set>`. `set.json` pins the release, `icons/` holds its SVG
  files under Iconify's names, `aliases.txt` its old names, `LICENSE` its license. `src/icons.rs` and `tsx/index.ts`
  are generated: never edit them by hand.
- `codegen/`: the generator of every set's `src/icons.rs` and `tsx/index.ts` (not published).
- `script/sync.ts`: syncs a set's `icons/`, `aliases.txt` and `LICENSE` from its pinned release.
- `examples/tsx-app`: a TSX app using several sets; `sets/lucide/examples`: the size measurements.

## API design

- **Rust and TSX are one API.** An icon has one name in both (`Lucide::ChevronDown`, `ChevronDown` of
  `nsh-icon-lucide`), and the TSX `<Icon>` takes the props Rust's `icon()` has setters for.
- **Names are upstream's, in PascalCase**, a style a suffix (`HomeSolid`, `HouseBold`): one type and one TSX module
  per set. Renamed icons keep their old name as a deprecated alias.
- **An unused icon costs nothing.** Every icon is a constant; nothing may list or look up a whole set unless the app
  turns on that set's `all` feature or names the icons with `icon_set!`.
- **Released names stay.** A set update that drops an icon keeps a deprecated alias when upstream names a
  replacement.

## Updating a set

1. Change `version`, `archive_url`, `sha256` and `icon_count` in `sets/<set>/set.json`.
2. `bun script/sync.ts <set>` writes `icons/`, `aliases.txt` and `LICENSE`.
3. `NSH_ICON_UPDATE=1 cargo test -p nsh-icon-codegen` regenerates `src/icons.rs` and `tsx/index.ts`.
4. Update the set's version and icon count in the README and in `src/lib.rs`'s table.

## AI-Assisted Contributions

AI-assisted contributions are welcome, including pull requests whose code was entirely generated by AI. What matters
is that the change is necessary, focused and validated; the contributor is responsible for the result.

Before opening a pull request, make sure that:

- The problem is real, and a new feature or set is within the scope above.
- The API and implementation follow the existing patterns.
- You reviewed the code and tested it: headless tests through the public API, `nsh check` and `nsh test` in
  `examples/tsx-app`, and a look on screen for anything visible.
- The diff is as small as practical: no unrelated refactors, cleanup or formatting. Reproduce a defect and fix its
  cause rather than hiding it behind retries or guards.

### Describe public API changes

A pull request that adds or changes anything public — a type, function, macro, prop, crate, feature, or an icon set's
names — lists it under `## Public API`, grouped by crate, with the signature as a reviewer would read it in the docs
and one line on what it is for. A change to a released item goes under `## Breaking Changes` with a `diff` block,
and says why it cannot be an addition.

## Commits and pull requests

All changes go through a pull request against `main`; nothing is pushed to `main` directly. Pull requests are squash
merged, so the pull request's title becomes the commit on `main`, with its number appended.

Commit subjects and pull request titles name the area first, then say what changed as an imperative sentence:

```
<area>: <What the change does>
```

- The area is the part of nsh-icon the change is about, in lower case: `icon` (the `Icon` type, `icon()`,
  `labeled_icon()`, `icon_set!`), `tsx` (the native module and `<Icon>`), a set by its name (`lucide`, `heroicons`,
  `tabler`, `phosphor`, `remix`), `sets` for a change to every set, or `codegen`, `sync`, `examples`, `skills`,
  `docs`, `ci`, `release`. Name one area only: for a change that spans several, name the part it is mostly about.
- The sentence starts with a capital letter, uses the imperative mood, has no trailing period and fits in about 72
  characters with its area. It says what the change does for an app, not which files moved.
- No conventional prefixes (`fix:`, `feat:`, `chore:`).
- The body (optional for small changes) explains why, wrapped at 72 columns.

Examples:

```
lucide: Update to Lucide 1.44.0
tabler: Keep the old names of renamed icons as deprecated aliases
tsx: Accept an imported SVG asset as the icon
icon: Draw a reactive icon only when its signal changes
sets: Add Material Symbols
release: Publish 0.1.1
```

### Reviewing

A review presents, in order: the pull request's purpose (the problem and the scope of the changes), whether the
requirement and approach are reasonable, then concrete findings, the validation performed and its limits. A pull
request that adds a set or public API is checked against "Scope" and "API design" before its implementation is
reviewed. A new set's review checks its license and that its files match its pinned release
(`bun script/sync.ts --check <set>`).

Every pull request that changes what is drawn includes a screenshot.

## Releases

A release is a pull request too:

1. A `release: X.Y.Z` pull request bumps the workspace's `version` in `Cargo.toml` (and `Cargo.lock`), the
   `nsh-icon` requirement of the sets' `nsh.json` when its minor version changes, and the version in the README
   where it appears.
2. After it merges, tag the merge commit on `main` as `vX.Y.Z` and push the tag. The
   [Release workflow](.github/workflows/release.yml) checks that the tag is the workspace's version, runs the tests,
   publishes `nsh-icon` and then each `nsh-icon-<set>` to crates.io, and creates the GitHub release with the changes
   since the previous one. A crate already published at that version is skipped, so a failed run can be re-run.

## Development and Testing

You need Rust (stable), the `nsh` CLI and [bun](https://bun.sh) for the sync script.

```sh
cargo test --workspace                                  # every crate, headless; the generated sources are current
cargo test --workspace --all-features                   # with the sets' `all` lookups
cargo clippy --workspace --all-targets --all-features   # no warnings
bun script/sync.ts --check                              # every set matches its pinned release
cd examples/tsx-app && nsh check && nsh test            # the TSX face, against this checkout
```

Look at any visible change on screen (`nsh run` in `examples/tsx-app`, or `nsh test --target <platform>` with a
screenshot).
